# Агентная логика — твоя (ML) часть пайплайна

Это не единоразовый вызов LLM, а последовательность шагов с сохранением
контекста между ними (требование ТЗ, слайд 7: Планирование → Работа с
инструментами → Контекст → Самопроверка). Дёшево-и-часто используем
маленькие модели, дорого-и-редко — модель с рассуждением (бюджет 500₽/день
на всю команду!).

## Какая модель на каком шаге и почему

| Шаг | Модель | Почему |
|---|---|---|
| Классификация новости по теме/отрасли | **Gemma 4 26B A4B** | простая задача классификации, дешёвая модель |
| Извлечение фактов из новости/аналитики (NER-подобное) | **Gemma 4 26B A4B** | извлечение информации — по списку её профиль |
| Скоринг релевантности новости клиенту (bulk, много новостей) | **Qwen3.6 35B A3B** | универсальная, обработка информационных материалов — основной рабочий конь ранжирования |
| Поиск неочевидных связей клиент↔событие (через группу компаний, контрагентов) | **DeepSeek-V4.1-Flash** | заявлена для "поиска взаимосвязей и анализа больших объемов информации" |
| Финальная персонализированная интерпретация (генерация текста под клиента) | **GLM-5.3-Flash** | задача повышенной сложности, нужны рассуждения — тратим дорогую модель только здесь, на уже отфильтрованных 1-3 событиях на клиента |
| Self-check (полнота/непротиворечивость готового текста) | **Kimi-K2.6** | обработка и анализ готового текста, дешевле второго прохода GLM |
| (опционально) анализ скан-таблиц/графиков из PDF аналитики | **Qwen3-VL-30B-A3B-Instruct** | единственная мультимодальная из списка |

Идея экономии: 85 525 компаний в данных, но клиентов с выручкой ≥15 млрд ₽
(крупный бизнес по ТЗ) — **всего 115** (см. `client_profiles.json`). Это и
есть реальная целевая аудитория демо — не нужно гонять LLM на всю базу.
Внутри одного клиента: дешёвая модель фильтрует 100+ новостей дня до 3-5
релевантных, дорогая модель пишет интерпретацию только по ним.

## Шаг 1. Planning (на входе: client_id, дата)

Промпт (Qwen3.6 35B A3B), системная роль агента-планировщика:

```
Ты — агент-планировщик сервиса персонализированной новостной аналитики
для крупного бизнес-клиента Альфа-Банка.

Дано (контекст клиента, JSON): {client_profile}

Определи:
1. Какие источники нужны: внешние новости (по каким topic_tags искать:
   industry_sector, sensitivities клиента), аналитика Альфа-Банка (RAG
   по Приложению 2 — какие темы искать: ставка/инфляция/сырьё/валюта/
   отрасль), данные о контрагентах клиента (нужны ли графовые связи).
2. Нужна ли дедупликация/обновление кэша новостей за последние N дней.
3. Верни план шагов в строгом JSON: {"queries": [...], "need_graph": bool,
   "need_bank_analytics_topics": [...]}
```

Выход сохраняется как контекст (`steps[0]` в `provenance`) и передаётся
дальше без повторного пересчёта — это и есть "Контекст" из требований.

## Шаг 2. Retrieval / инструменты

Инструменты, которые вызывает агент:
- `search_news(query, date_range)` — ваш парсер (Аналитик 2)
- `rag_search(query, corpus="alfa_analytics")` — поиск по Приложению 2
  (9 PDF из материалов — инфляция, ставка, сталь, золото, FI strategy,
  потребление, макростатистика)
- `get_client_graph(client_id)` — контрагенты из `df_Uid_payment_hack.csv`
  (уже посчитано в `client_profiling.py`: `counterparty_count`,
  `inbound/outbound_payment_volume`)

## Шаг 3. Ranking (дешёвая модель, bulk)

Промпт (Gemma 4 26B A4B / Qwen3.6 35B A3B), на вход — пачка новостей +
профиль клиента:

```
Для каждой новости оцени релевантность клиенту от 0 до 1 и укажи,
какие признаки клиента сработали (из списка: industry_sector,
sensitivities, fx_exposed, revenue_bucket, region, products).
Не пересказывай новость — только оценка + причина. Верни JSON-массив
{event_id, score, matched_client_features}.
Клиент: {client_profile}
Новости: {news_batch}
```

Берём top-3 по score ≥ порога на клиента в день — дальше уже дорогая модель.

## Шаг 4. Generation — персонализированная интерпретация (GLM-5.3-Flash)

```
Ты формируешь персонализированный бизнес-инсайт для представителя
крупного бизнеса (ЛПР) в интерфейсе Альфа-Бизнеса. НЕ пересказывай
новость — объясни её значение именно для этой компании, опираясь на
её контекст и на аналитику Альфа-Банка. Ответь на 6 вопросов:
1) что произошло (только факты), 2) почему это важно для клиента,
3) какие риски/возможности возможны, 4) какие действия могут быть
релевантны, 5) как это оценивает банк (используй переданную аналитику
Альфа-Банка, если релевантна), 6) на чём основан вывод (явная ссылка
на источники). Чётко разделяй: что из данных клиента, что из аналитики
банка, что — твой вывод. Верни JSON по схеме PersonalizedInsight.

Профиль клиента: {client_profile}
Событие (факты): {event_facts}
Релевантная аналитика Альфа-Банка (RAG-выдержки): {bank_analytics_snippets}
```

## Шаг 5. Self-check (Kimi-K2.6)

```
Проверь интерпретацию на: (а) полноту — есть ли ответы на все 6 вопросов,
(б) непротиворечивость — не противоречит ли вывод исходным фактам,
(в) обоснованность — у каждого вывода есть источник в basis_for_conclusion.
Если есть проблема — верни {"ok": false, "issues": [...], "action":
"re-retrieve"|"re-rank"|"re-generate"}. Если всё ок — {"ok": true}.
```

При `ok: false` агент повторяет соответствующий более ранний шаг
(не всю цепочку) — это и есть "Самопроверка и адаптация" из ТЗ.

## Безопасность (п.6 ограничений в ТЗ — для прототипа достаточно описать)

- Разграничение доступа: агент получает **только** `client_profile`
  того клиента, под которым залогинен пользователь (никаких чужих UID в
  промпте) — фильтрация на уровне API перед вызовом LLM.
- Чувствительные данные (платежи, контрагенты) не уходят во внешние
  источники — только в промпт LLM из разрешённого списка, без логов с
  конкретными суммами в открытом виде вне защищённого хранилища.
- Журналирование: каждый шаг пишет `provenance.steps[]` — кто вызвал
  какой инструмент, с какими входами/выходами (для трассируемости, п.12).
- Лимиты: жёсткий дневной бюджет токенов на клиента/команду, чтобы не
  выйти за 500₽/день.
